## Model Log Book — Charter and Entry Conventions

This package is the running record of **changes to and reviews of the Smart Robot Car Capella model** (`tkomarOSP/SmartRoboticCar`, branch `master`). It answers three questions later: *what changed, why, and who looked at it.*

### What goes here

| Record this | Entry type | Typical trigger |
|---|---|---|
| A change applied to the model (added/renamed/moved/deleted elements, new allocations, changed properties) | `decision` if a choice was made between options; otherwise `observation` | After `apply_model_patch`, and again after `push_model_changes` |
| A review of the model or a part of it (completeness, consistency, `verify_model` findings, peer review) | `observation` | After a review pass or verification run |
| Something learned from a change or review that should shape future modeling | `lesson_learned` | When a pattern, pitfall or convention emerges |
| Open problems found but not yet fixed | `issue` | When a review finds something to follow up |

### Entry template — model change

- **Phase / layer:** OA / SA / LA / PA (or Requirements)
- **Elements affected:** name and UUID for each (confirm UUIDs before patching)
- **Change:** what was done, in systems-engineering terms (e.g. function allocated to component, exchange added)
- **Rationale:** why; alternatives considered
- **Verification:** result of `verify_model`, or "not run"
- **Git:** pushed to `master`? commit reference if known
- **Author / requested by**

### Entry template — review

- **Scope:** phase(s) and elements reviewed
- **Method:** `verify_model`, manual walkthrough, peer review, etc.
- **Findings:** numbered, each marked *ok / issue / question*
- **Follow-ups:** what must change, and a reference to the entry that records the fix
- **Reviewer / date**

### Conventions

- One entry per change set or per review, not per element — keep related edits together.
- Write the entry **after** the action and cite real entry ids (e.g. `model_log_book/dec-0002`), since numbers are per package and can't be predicted.
- When a review finding is fixed, record the fix as a new entry and reference the review; don't rewrite the review.
- Never put credentials in an entry; use `{{GITHUB_PAT}}` if a placeholder is ever needed.
- Model-modeling notes go here in `knowledge-repo`, never into the model repo itself.
